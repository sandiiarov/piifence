## Direction options (not planned; for the maintainer to weigh)

- **Rules first, model second, for secrets.** In the `secret-rules` mode the model is never loaded and a request costs a gitleaks subprocess per block; in model modes the CPU model (about 90 tokens/s) is the latency floor (21 s at turn 45 before the cache existed). After plan 006, the rules-only mode will catch most formats; measuring its recall against the model modes with the suite would show whether the model should become an opt-in second pass for secrets. Trade-off: passwords without a keyword and novel token shapes are model-only.
- **A scored benchmark instead of pass/fail cases.** The suite answers "did it leak"; a precision/recall harness over a public dataset (see the table) would tell whether a change trades recall for precision. Trade-off: dataset licences and a day of harness work.
- **Persist the cache across launches.** See the table row; the main design question is where the file lives and how it is bounded, not whether it is safe.

## Findings considered and rejected

- The env-reference guard suppressing real secrets next to `process.env.X`: a direct probe did not reproduce it. Re-open only with a failing example.
- gitleaks losing findings near its chunk boundary (claimed around 90 KB): measured with single-line keys and multi-line text at 65, 90, 100, 131 and 200 KB offsets; every key was found. Re-open only with a reproducing input.
- Relaxing the default `generic-api-key` delimiter: a keyword-based rule without a trailing delimiter over-matches prose; plan 006 relaxes only prefix-identified tokens.
- A bare high-entropy hex rule: would flag md5sums, git SHAs and digests (all suite negatives). The model stays the only detector for `hex32_bare_no_keyword`.
