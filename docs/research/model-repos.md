Scope: `purebyte-ai/purebyte`, `purebyte-ai/purebyte-train`, `apartejs/aparte-secrets-model`, `SpecterOps/DeepPass2`, `valendra-tech/valendra-privacy-filter`, and the cards in `hf:`. Everything was read only; nothing was built, installed or run from these repos. No secret values are reproduced; shapes are described instead. "(inference)" marks my own conclusions rather than statements from the source. Sections are ordered by usefulness to piifence.

## 1. Quick wins for piifence (ranked)

1. Mask every occurrence of a detected value across the whole request body, not just the span the detector found (aparte `mask()`, `apartejs/aparte-secrets-model/packages/secrets/src/secrets.js`: "a value found once is masked everywhere it appears ... the model may only flag the occurrence whose context gives it away"). Apply it across all messages and tool results of one `/v1/messages` body, and keep a per-session set of already-found values so later requests mask them too (inference). This covers part of "hint on the line above", "token used as host label" and "secrets split across messages" whenever any one occurrence was caught. Cheap, no model change.
2. Base64 decode-and-rescan (purebyte `purebyte-ai/purebyte/engine/src/detect/code_rules.cpp` `readable_base64_blobs`): for each maximal run matching `[A-Za-z0-9+/]{32,}={0,2}`, strictly decode; if the decoded bytes are at least 12 long and more than 90% printable ASCII/tab/LF/CR, drop model spans inside the blob and rescan the decoded text (if at least 24 bytes) as its own document, mapping hits back to the whole blob. A decoded blob matching `^[A-Za-z0-9._@+-]{1,64}:[^\s:]{6,128}$` is a `user:password` (Docker `auth`, Basic header) and is masked whole. Non-readable blobs (images, binary) are base64 dumps: a natural guard for that FP class (inference; purebyte itself leaves them to the model). Extend the same idea to hex (decode even-length hex runs to printable ASCII) and percent-encoding, which purebyte does not have (inference).
3. Drop spans entirely inside a `data:<type>/<subtype>(;param)*;base64,` payload of at least 16 chars (purebyte `code_rules.cpp`, data-URI skip). Fixes a slice of the base64-dump FPs.
4. UUID policy (purebyte-train `purebyte-ai/purebyte-train/data/pbdata/creddata_stream.py` around lines 75-86): a UUID is a secret only under an unequivocal credential name. Credential-name regex (case-insensitive): `api[_-]?key|apikey|token|secret|passw|pwd|auth|licen[cs]e[_-]?key|access[_-]?key|private[_-]?key|credential|bearer|x-api-key|signing[_-]?key`; id-name regex: `(^|[_.\-])(id|uuid|guid)$|Id$|ID$|postman|uuid|guid`. For piifence, apply it to the nearest "name" in a wider sense: the JSON/YAML key, the markdown table column header of that cell, the nearest preceding `#` heading, and the preceding prose line (inference). That converts the "UUID key in a table column" and "## Webhook secret" leaks into key-rule hits.
5. Cheap non-secret prefix guards taken from the purebyte-train hard-negative families (`purebyte-ai/purebyte-train/specialists/secrets-code/secretsgen/credentials.py`, `NEGATIVE_WEIGHTS` around line 793): SRI `sha256-`/`sha384-`/`sha512-` base64 and `sha256:` + hex64 digests; crypt-style password hashes (`$2b$`/`$2y$` bcrypt, `$argon2id$`, `$6$`, `pbkdf2_sha256$`, `{SSHA}`); encrypted blobs (SOPS `ENC[AES256_GCM,`, `$ANSIBLE_VAULT;1.1;AES256`, `vault:v1:`, jasypt `ENC(`, Fernet, sealed-secrets, age); `PublicKeyToken=` hex16; public keys and fingerprints (`ssh-ed25519`, `ssh-rsa`, `SHA256:`, colon-hex); redacted keys (provider prefix followed by `*`, `X`, `.`, `<...>`); regex sources of detectors (`ghp_[A-Za-z0-9]{36}`, `(?i)`, `\b`); alphabet tables (`BASE62`, base58, Crockford, keyboard rows); hex dumps 96+ chars with `FF` padding. Decide explicitly on crypt hashes: Nosey Parker (DeepPass2 rules) reports them as findings because they are crackable (inference: masking them is the safer gateway choice).
6. Benign-name vs credential-name contrast as a test generator: purebyte-train builds benign names as prefix x root x suffix (`cached_`/`expected_`/`upstream_` x `commit`/`checksum`/`etag`/`trace`/`request`/`nonce`/`invoice` x `_id`/`_hash`/`_sha256`/`_etag`/`_integrity`/`_fingerprint`, `credentials.py` around lines 774-776) and puts the same value shapes (hex 7/16/32/40/64/128, UUID, ULID, nanoid-21, snowflake 19 digits) under benign names as negatives and under credential names as positives. Port it as a Rust fixture generator: same random value under both name kinds, assert piifence masks only the credential one. Directly targets hash/id FPs and 32-hex leaks with a keyword.
7. Span cleanup rules (purebyte `purebyte-ai/purebyte/engine/src/detect/code_rules.cpp`, profile order in `profile_secrets_code.cpp`): merge spans at most 3 bytes apart; split a span at each line that starts a new assignment (`^([ \t]*[-+]?[ \t]*["']?[A-Za-z_][A-Za-z0-9_.\-]{0,47}["']?[ \t]*(?::=|=>|=|:[ \t])[ \t]*)(?=\S)`); snap to the enclosing balanced quote literal (at most 90 bytes); otherwise snap to the whole assignment value if at most 40 bytes longer; widen to the whole PEM block. Valendra's model-gated variant (`valendra-tech/valendra-privacy-filter/src/valendra_privacy_filter/inference/detector.py` `_extend_secrets_to_whitespace_runs`): grow a SECRET fragment to its whitespace-delimited run (strip wrapping `"'«“‘([{<` and trailing `"'»”’)]}>.,;:`) only if the summed log-prob of tagging the whole run as SECRET beats "all O"; a Rust port exists in `.../examples/candle-wasm/src/decode.rs` `reconcile_secrets`. Useful for partially tagged upper-case short passwords and prefixed tokens.
8. Operating bias before decoding instead of a post-hoc threshold: purebyte adds a per-label bias to non-O log-probs before constrained BIOES Viterbi (`engine/src/heads/tag.cpp`, `heads/bioes.cpp`), stored per type in the model file, chosen on a held-out "select" split with "highest precision subject to recall >= 0.60" (`purebyte-ai/purebyte-train/training/pbtrain/eval/operating_point.py`, grid -6..6, error if optimum sits on the grid edge). Per-label bias would let piifence be aggressive on `password` and conservative on generic hex labels.
9. Report vs redact split: purebyte still hides spans that its rules dropped (doc examples, data URIs, allow lines) in redacted output (`profile_secrets_code.cpp`, `add_hidden`). For a gateway, a guard that "drops" a span could instead downgrade it to "redact only if a second signal agrees" (inference).
10. Regex additions from DeepPass2's Nosey Parker set (`SpecterOps/DeepPass2/utils/regexRules.jsonl`): prose rules `the (default )?password is '...'`/`"..."` and `the (default )?password for (the )?(user|username) '...' is '...'` (np.generic.11-14) with a restrictive first-char class `[^'\n\#$|"{<+ ()\\]` to skip interpolations; `secret.{0,20}\b([0-9a-z]{32,64})\b` (np.generic.1); `netrc` `machine ... login ... password ...`; `Authorization: Basic`; Postgres URI; .NET `NetworkCredential`; PsExec `-p`. The quoted-password first-char exclusion `[^$<%@.,\s+'"(){}&/\#\-]` is a good placeholder filter for the key rule. Note none of these catch unquoted prose passwords such as "the wifi password for the office is X" (inference): add a prose rule `(?i)\b(password|passcode|passphrase|pin|пароль|contraseña|mot de passe)\b[^\n.]{0,40}?\b(is|est|es|—|:)\s+(\S{4,64})` gated by a non-dictionary-word or mixed-character-class check (inference, untested).
11. External evaluation without training: run piifence on aparte `chat-fresh` and `chat-fresh-json` (chat prose and JSON-escaped prose, EN/FR, with labelled decoys), and on CredData TEST via purebyte's `score.py` generic `flags` JSON format. See section 5.

## 2. Ideas mapped to the measured weak spots

| Weak spot | What the repos offer |
|---|---|
| 32-hex with no keyword | Nobody detects it by design: purebyte-train only makes a bare value positive if it is "decidable" from the value itself (provider prefix, `-----BEGIN`, `scheme://user:pass@`; `secretsgen/task.py` `_DECIDABLE` around lines 18-20). aparte card: "Unknown providers rely on context". Best available lever is quick win 1 (mask repeats) plus a session memory of masked values (inference). |
| Hint on the line above in prose | No generator covers it. purebyte-train's `extra_lines` blocks put up to 5 generated lines near the secret but the name is on the value's own line. aparte trains on LLM-written chat templates and WildChat insertions; its 256-token window sees the previous line, so it may handle this (inference, untested). Write our own templates: hint sentence, newline, bare value (inference). |
| UUID key in a table column / under "## Webhook secret" | purebyte UUID policy (quick win 4) + markdown table rows and prose in `_auth_header` (`credentials.py` around line 1532) as the only table/prose forms. Extend the key rule to headers/headings (inference). |
| Password under JSON `"name"` | purebyte treats `name` as a non-credential name (`_NON_CRED_NAMES`) so it would also miss it. Only value-shape cues can help (mixed classes + symbol) (inference). |
| Token used as host label | Not addressed anywhere; quick win 1 masks it if the token was found elsewhere. |
| Plain-word passphrases | purebyte's own measurement: word-like passwords recall drops to 0.389 when CredData's random replacement values are swapped back for originals (`purebyte-ai/purebyte/benchmarks/RESULTS.md` lines 71-94). DeepPass2 used CrackStation "real human" breached passwords as positives and still reports weaker recall on dictionary words. purebyte-train `_password_g1` (word, word+digits, leet, Capitalized+year+symbol, two words concatenated, PINs; `credentials.py` around line 1357) and `_weak`. No one generates space-separated passphrases. |
| Passwords in Russian prose | Nothing. aparte EN/FR only, Valendra EN/ES, purebyte-train Spanish words only. Must be built ourselves. |
| Secrets split across messages | Nothing in model repos; quick win 1 with a session-wide value set. |
| Password in neutral URL query param | purebyte-train treats neutral query params as negatives (only `?password=`, `?secret=` in otpauth are positives). Valendra labels a `?token=` value inside a URL. No help for neutral params (inference: rely on value shape). |
| URL/base64/hex-encoded secrets | purebyte runtime base64 rescan (quick win 2); purebyte-train `_sec_obfuscated` (`\xNN` escapes, hex of ASCII, base64 of the secret, 8-char chunks joined with `' + '`; `credentials.py` around line 176) and `decoded` forms (`b64decode("..")`, `bytes.fromhex`, `atob`, `xxd -r -p`) label the encoded literal as the secret. 10% of passwords percent-encoded in the PII URL generator. |
| Upper-case short passwords | purebyte-train has 8-16 mixed-case alnum with guaranteed upper/lower/digit, but no all-upper-case family; aparte has none visible. Add `[A-Z0-9]{8,12}` under password context, contrasted with base32 OTP secrets and upper-case 10-char app ids as negatives (inference). |
| FP: hashes/digests, ids | quick wins 5 and 6; aparte card shows a commit SHA and a request UUID correctly ignored. |
| FP: base64 data dumps | data-URI skip, non-readable base64 blobs, aparte `negatives.jsonl` (byte arrays, URL-encoded strings, base64 images, hashes, minified JS). |
| FP: variable names | aparte v1.1 cut FPs 4x (0.69 to 0.17 per kLOC) by adding docs and sources of third-party npm packages as negatives; v1 flagged camelCase identifiers, CSS values, and words after an escaped `\n` in JSON. |
| FP: app-id listings | purebyte-train `PAIRS` (around line 422): public half of a provider pair is a negative (Stripe `pk_`, Algolia app id, Mailgun pubkey, Supabase anon JWT), secret half positive. |
| FP: ordinary phrases | aparte chat-fresh has 110 messages that talk about a password without giving one, and `chat_phrases.jsonl` trains on "password for <service>" sentences with and without a value. aparte still tags the noun after "password of the" in French (card example) - a good regression case. |

## 3. purebyte-train: data generator and training recipe (most reusable for fine-tuning and test generation)

Sources: `purebyte-ai/purebyte-train/specialists/secrets-code/secretsgen/credentials.py` (1,769 lines), `.../secretsgen/task.py`, `.../secretsgen/catalog.py`, `.../specialists/secrets-code/recipes/secrets-code-1.0.0.yaml`, `.../specialists/secrets-code/README.md`, `.../specialists/secrets-code/plugin.py`, `.../data/pbdata/creddata_stream.py`, `.../data/README.md`, `.../training/docs/pitfalls.md`, `.../training/docs/recipes.md`, `.../training/docs/evaluate.md`, `.../training/pbtrain/eval/operating_point.py`, `.../training/pbtrain/data/leakage.py`, `.../specialists/pii/piigen/forms.py`, `.../specialists/pii/piigen/lookalikes.py`, `.../specialists/pii/piigen/rules.py`. License: Apache-2.0 code.

Window construction (`task.py` around lines 33-118): take a real 512-byte code/config window from pinned public repos; insert one generated line on a line boundary, positive or negative with 50% prior; in half the windows add up to 5 extra generated lines (all "traps" in a negative window, 50% positive in a positive one); half of the negative neighbour lines are replaced with real corpus lines; a bare value without name is used only when "decidable" from the value itself (`_DECIDABLE`: provider prefix, `-----BEGIN`, `scheme://user:pass@`). The span covers the value bytes only (no quotes); a URL credential is widened to the whole URL in secrets-code while the PII generator labels only `user:password` (inconsistent conventions; choose one for piifence). Multi-line PEM is one span. An encoded secret's span is the encoded literal. Train/select/test come from disjoint byte ranges of the corpus.

Positive value mix (`credentials.py` around lines 320-328): 38% provider-prefixed values sampled from 222 gitleaks rules and validated against the rule (`catalog.py`); 44% generic (`_sec_generic`: hex 32/40/48/64 lower or upper, base64 24-64, alnum 20-48, base64url 32-56, JWT, hex32-hex16, alnum+symbols 16-32); 12% connection strings (URI userinfo, Redis URIs with an empty user and a password before `@`, JDBC `?password=`, MSSQL `Password=`/`Pwd=`, Azure `AccountKey=`, libpq `key=value`, `Data Source=...;PWD=`); 6% PEM. 11% of lines use obfuscated values (`_sec_obfuscated`: `\xNN` escapes, hex of ASCII bytes, base64 of the secret, 8-char chunks joined with `' + '`).

Password families: `_password_short` (8-16 mixed-case alnum guaranteed upper+lower+digit; alnum with one symbol; word+leet+year+`!`); `_password_g1` (Spanish/English word list: bare word, word+digits, leet, Capitalized+year+symbol, two words concatenated, classic weak passwords, 4-8 digit PINs, random alnum, class-preserving obfuscation); `_weak`. Bare dictionary words are positive only under an unambiguous password name (`_NM_UNAMBIGUOUS`, includes `pin`, `clave`, `contrasena`); the contrast negative swaps the name for a non-credential name (`username`, `host`, `theme`, `mascot`, `codename`) or the value for a marker (`_contrast_g1`: marker, interpolation, empty, code reference).

Forms (36 languages and config formats, `FORM_WEIGHTS` around line 893): assignment, kwargs, header, comment, k8s base64 `data:`, decode-call wrapping (`b64decode`, `bytes.fromhex`, `atob`, `xxd -r -p`), diff, non-assignment (CLI flags, `.netrc`, `.pgpass`, `docker login -p`, SQL `CREATE USER ... PASSWORD`, log and exception lines that print the value), nested 3 levels in JSON/YAML/object literals, directive syntax without `=` (`requirepass`, `wpa-psk`, netrc, base64 `user:pw` under `auth`), XML `<password>` tags, `curl -u`, `sshpass -p`, `redis-cli -a`, `mysql -p`, `smbclient -U u%pw`, credential tuples, auth headers in raw HTTP, curl, client code, markdown table rows and prose ("Send the header `Authorization: Bearer X` with every request."), short passwords in DSNs inside f-strings/Sprintf/template literals, unnamed values passed positionally (`pyotp.TOTP("..")`, `otpauth://...?secret=`, NATS nkey seeds, `Github("..")`, `TeleBot("..")`), .NET `<add key="ApiKey" value=..>` and `connectionString="...Password=..;"`.

Hard-negative families with weights (`NEGATIVE_WEIGHTS`): benign_entropy 22, environment 20, placeholder 17, public 14, redacted 14, ordinary_short_value 14, pattern 13, password_hash 11, public_pair 10, crypto 9, curated_fp 9, url_without_credential 9, empty 9, reference 8, table 8, encrypted 8. Details: benign_entropy = hash/id shapes under benign names (quick win 6); public = `pk_live_`/`pk_test_`, ssh public keys, `SHA256:` and colon-hex fingerprints, PUBLIC KEY/CERTIFICATE PEM, `did:key`, `0x`+hex40 wallets, base58 addresses, the well-known jwt.io example header and payload; password hashes (bcrypt, argon2id, sha512crypt, pbkdf2, SSHA, scrypt, crypt) under password-hash names; encrypted = SOPS, sealed-secrets, ansible-vault, git-crypt, `vault:v1:`, jasypt, Fernet, age; redacted = provider prefix followed by masking characters, or a few visible chars then mask; pattern = detector regex sources, PEM header strings inside error messages; crypto = IV/nonce/salt/test vectors (including the well-known NIST AES test key) and long hex dumps with `FF` padding; table = alphabet constants; placeholder = `YOUR_X_HERE`, `<x>`, `[x]`, `{{x}}`, 49 stock/placeholder passwords, `not-a-real-key`, repeated chars, repeated `deadbeef`-style hex words, documented AWS-style keys ending in `EXAMPLE`; environment = `os.environ[..]`, `${{ secrets.X }}`, `{{ .Values.x }}`, `credentials('x')`, `vault.read` in 30 languages/CI systems; url_without_credential and web negatives = percent-encoded query strings, `%5B%5D` arrays, percent-encoded Japanese, HTML entities, SRI digests; ordinary_short_value = cookies, `max-age=`, emails, MIME types, ISO dates, semver, paths under protocol names, and ordinary words under credential names (`bearer`, `HS256`, `bcrypt`, `required`, `keyring`); .NET look-alikes (`PublicKeyToken=`, resource strings whose text says "Enter your API key", "Mot de passe", "Passwort vergessen?"); connection strings without userinfo or with `${DB_PASSWORD}`/`****`; PAM/password-policy directives; base64 of benign text under `data`/`payload`/`icon` as the contrast for base64 `user:pw`.

Real data and mining: a CredData DEV stream (24,000 windows from 117 DEV repos, 25% of each batch; per 4 windows, two around a credential, one around a labelled FP, one background); in half of credential slots the value is re-planted with a generated value of the same form and the same hole also gets its contrast negative (`creddata_stream.py` around line 274). Families added after error analysis: `password_named_short`, `auth_header`, `url_short_password`, `unnamed_values`, `dotnet_resources`. Mined negatives (real windows a released model flagged) replace up to 50% of negatives, with the warning "Blind negative mining mines real credentials. Mine with a filter for anything credential-shaped." (`pitfalls.md`).

Chat and multilingual: none in secrets-code. The PII specialist has three prose templates per language (`piigen/forms.py` around line 355: "The wifi password is {}.", "Use the key {} to log in.", "The access token is {}." plus Spanish) and uses hex32/40/64 and UUIDs as SECRET negatives (`piigen/values.py` around line 550). `lookalikes.py` labels ambiguous look-alikes as IGNORE (-100) rather than O, which avoids contradictory supervision; useful for hex/UUID cases we cannot label confidently.

Methodology lessons: synthetic scores did not predict real ones ("recall 0.98 on the synthetic battery was 0.31 on real code", `pitfalls.md`); more capacity raised FPs on real code when labels were synthetic; bidirectional mode did not help; about one seed in six is a bad tail seed, so train several seeds and judge by the worst; a shuffled-span control (F1 0.000) and an entropy-over-quoted-literals rival (F1 0.330; `plugin.py` around lines 110-131, literal 12-90 chars, entropy threshold swept 2.4-4.4, placeholder regex `YOUR_|_HERE|CHANGE|changeme|xxxx|TODO|REDACTED|\*\*\*|not-a-real|replace-with|dummy|example|test|placeholder|INSERT_|^0+$|^a+$|abcdef0123456789`) are the sanity baselines. Leakage guard (`leakage.py`): 64-bit hashes of 64-byte content-defined blocks; any block shared with a test exam fails the data build. The authors admit the released seed was chosen on a false-alarm exam with TEST scores in view and that both pre-registered false-alarm criteria failed (360-571 findings against a cap of 129).

## 4. purebyte runtime (secrets-code model + post-processing profile)

Sources: `purebyte-ai/purebyte/README.md`, `.../models/secrets-code.md`, `.../models/models.json`, `.../docs/architecture.md`, `.../docs/performance.md`, `.../benchmarks/RESULTS.md`, `.../benchmarks/creddata/README.md`, `.../engine/src/detect/profile_secrets_code.cpp`, `.../engine/src/detect/code_rules.cpp`, `.../engine/src/detect/common.h`, `.../engine/src/detect/code_files.cpp`, `.../engine/src/detect/redaction.h`, `.../engine/src/heads/bioes.cpp`, `.../engine/src/heads/tag.cpp`, `.../cli/cmd_serve.cpp`, `.../MODEL_LICENSE.md`; card `hf:purebyte/secrets-code`.

Model: byte-level (raw UTF-8 bytes, no tokenizer) ternary-weight Mamba-2-style SSM, four `ssm_v2` blocks of width 256, weights in {-1,0,+1} with a scale per 128 weights; BIOES tag head with one label plus a window-level `choice` gate (max pooled) that skips windows predicted clean. 1.93M params, GGUF 1,028,704 bytes. Windows 512 bytes, stride 384; inputs under 24 bytes are not analysed (inference: so short chat strings like a lone password are never scored). Output: byte spans with line/column, confidence (mean probability of the chosen labels), masked snippet; one type `secret`. Interfaces: C API, CLI, Python bindings, HTTP server `POST /v1/scan`, `/v1/decide` (inputs up to 4 KB), `/v1/redact`. Redaction is consistent (`[secret_1]` per distinct value; numbering starts above markers already present). CPU only, AVX2/NEON, bit-identical at any thread count.

License: runtime Apache-2.0; weights under "PureByte Model License 1.0": free on hardware you control, no redistribution, no building models from the weights (no fine-tuning or distillation), no hosted service whose main value is the model. For piifence: users would have to pull the weights themselves; we could retrain our own with the Apache-2.0 training repo instead.

Speed (`docs/performance.md`, Ryzen 9 5900X): 64 B 2.97 ms single-thread (0.82 ms default threads), 256 B 12.0 ms (2.81), 1 KB 50.4 ms (10.5); bulk about 131 KB/s at 187 MB peak RSS. Too slow for every byte of large tool results (about 0.8 s per 100 KB); usable as a second opinion on candidate regions (inference).

Published evaluation (`benchmarks/RESULTS.md`): Samsung CredData at commit `c09c0c5`, split 50/50 by repository with seed 20260922; headline on 164 TEST repos (four overlapping training excluded), 4,219 positive credential lines, CredData line rule. secrets-code P/R/F1 0.879/0.729/0.797; 3-seed ensemble with 2-of-3 votes 0.879/0.741/0.805; gitleaks 8.30.1 0.905/0.207/0.337; trufflehog 3.97.6 0.578/0.025/0.047. With CredData's obfuscated values swapped back for the original values: recall 0.729 to 0.583, F1 0.694; passwords 0.881 to 0.482; word-like passwords 0.870 to 0.389; auth headers, URL credentials, private keys and UUIDs barely move. Lesson: random-replacement benchmarks overstate password recall; test piifence with word-like passwords. Per family (obfuscated TEST): password R 0.88 P 0.82; token/bearer/JWT R 0.69 P 0.91; UUID/salt/nonce R 0.12 P 0.98 (deliberate); URL credentials/Basic R 0.99 P 0.99; provider patterns R 0.85 P 1.00; generic key R 0.82 P 0.72; PEM R 0.90 P 0.94. DEV error analysis: values with no name next to them recall 0.79; FPs were 48/107 short ordinary values under credential-like names, 19 symbol-heavy strings, 18 multi-line blocks, 10 hex/base64 under a name, 7 references/function calls. On credential-free repos the real errors were mostly integrity hashes in `package-lock.json`, base64 images in notebooks, demo passwords and example `Basic` headers in doc comments: the same FP classes as piifence. Operating points: `--bias 0` best DEV F1; `--bias -2` gives TEST P 0.932 R 0.663.

Post-processing profile, in order (`profile_secrets_code.cpp` header: "The order of these steps matters: it decides which of two overlapping candidates survives"): (1) constrained BIOES Viterbi with operating bias (user scalar or per type, else per-type vector in the model file, O never biased); (2) readable-base64 rescan and `user:pass` decode (quick win 2); (3) data-URI skip (quick win 3); (4) span cleanup: merge within 3 bytes, split at assignments, snap to literal / value, PEM block widening, drop spans overlapping an earlier finding (quick win 7); (5) documentation-example allowlist: fixed substrings for the AWS documentation example key pair (shapes ending in `EXAMPLE` / `EXAMPLEKEY`) and Stripe's published doc test keys, matched with ±4 bytes margin, disabled by `--keep-examples`; per-line `purebyte:allow` marker; (6) rule-dropped spans still hidden in redacted views (`add_hidden`); (7) ensemble `vote_by_line`: findings on the same line with overlapping columns count as one, kept when at least `votes` distinct members report it; (8) path-based severity (test, spec, fixtures, examples, docs, mock, e2e, `*.md`, `test_*.py`, `*_test.go` become warnings; for piifence a Read tool_use path is a weak available signal, inference). No hex or percent-encoding decoder exists (inference from reading the rule files).

## 5. aparte-secrets (apartejs/aparte-secrets-model): 169K-param chat secret tagger

Sources: `apartejs/aparte-secrets-model/packages/secrets/src/secrets.js`, `.../python/aparte_secrets/reader.py`, `.../packages/secrets-cli/src/config.js`, `.../packages/secrets-cli/src/scan.js`, the JSON header of `.../packages/secrets/model/secrets-v1.1-int8.bin` (read as bytes, not run), and the cards `hf:apartejs/aparte-secrets`, `ds__apartejs__aparte-secrets-gold.md`, `ds__apartejs__aparte-secrets-data.md`.

Architecture (from the model header): 2-layer, 4-head transformer encoder, dim 64, factorised token embedding (4096-token byte-level BPE, 16-dim embeddings projected to 64), sinusoidal positions relative to the window, plus a learned "length class" embedding per pre-tokenizer unit (log2 of the unit's non-blank code-point count, 9 classes). 168,597 parameters; int8 file is about 196 KB. Window 256 tokens, stride 192. Labels: BIOES over 5 subtypes `password, api_key, token, private_key, other` (21 classes). Output: character spans `{start, end, text, subtype, score}`. Runtimes: pure JS (no deps), numpy reference reader, Kotlin, Swift. License MIT (code and weights); datasets ODC-BY 1.0. Languages: English and French only.

Speed (card, one CPU core): about 12.9 ms per 250-char chat message in Node, 86 µs per character of code (so roughly 86 ms per KB). That is slow per byte for big tool_result outputs because attention is naive O(L²) JS, but fine for chat-sized strings.

Decoding ideas worth copying. (1) "Unit" decisions: the text is first split by the pre-tokenizer regex ` ?[\p{L}\p{N}_\-]+| ?[^\s\p{L}\p{N}_\-]|\s+(?!\S)|\s+`, and the logits of all BPE tokens of a unit are averaged, so a label is decided per word-like run or per single punctuation char, never mid-word (`secrets.js` `detect()`: "one decision per unit inside the window: mean of its tokens' logits, then log-softmax"). (2) Overlapping windows are averaged in log-prob space per token, then per unit. (3) Constrained BIOES Viterbi with one subtype per span (`transitions()` sets disallowed moves to -1e9; spans must start with B/S and end with E/S). (4) Span score = `min over units of (1 - P(O))` (header `"decoding":{"score":"min over units of 1 - P(O)"}`), i.e. the weakest unit decides, which is a conservative score that piifence could use instead of a mean. (5) Leading whitespace is trimmed off spans. (6) `mask()` masks every other occurrence of a found value anywhere in the text: "a value found once is masked everywhere it appears: leaving a second copy in clear would defeat the purpose (the model may only flag the occurrence whose context gives it away)". This directly addresses piifence's "hint on the line above"/"token used as host label"/"split across messages" leaks if applied across the whole request body (all messages), not per string.

Policy after the model (CLI, `config.js`): `minScore: 0.5` default; ignore list (exact strings or `/regex/flags`); inline allow markers `aparte-secrets:ignore`, `gitleaks:allow`, `pragma: allowlist secret`; baseline file; skip files over 1 MB and lockfiles / `*.min.js` / `*.map` / `go.sum`. Large files are split into 16,000-char chunks with 2,000 chars of overlap; a span belongs to the chunk that owns its start (`scan.js`).

Published numbers (card). chat-fresh (440 EN/FR WildChat messages with LLM-inserted values, 396 secrets, 110 messages that talk about a password without giving one; written after training was frozen): v1.1 int8 strict P/R/F1 0.76/0.76/0.76, password recall 0.82, recall on unseen providers 0.93, false alerts 11/110. On the same set gitleaks 8.30.1 gets F1 0.29 (password recall 0.00, 0 false alerts), detect-secrets F1 0.27, OpenAI privacy-filter F1 0.53 with 55/110 false alerts. Same messages serialised as JSON (escaped `\n` and quotes, "chat-fresh-json"): F1 drops to 0.59, which is exactly piifence's input shape (tool_result strings often contain escaped JSON), so this is a warning that JSON-escaping costs about 17 F1 points for a small model. Clean repos (1,387 files, 218,493 lines of two secret-free public repos): 37 false alerts (0.17 per 1,000 lines) vs gitleaks 5 and detect-secrets 13. CredData long files (65 files, 131 secrets): recall 0.65, 1.5 FP/kLOC, F1 0.64. CredData lines relabeled so that UUIDs are not secrets: span F1 0.72, line F1 0.85. int4 file is noticeably noisier on code (0.44 FP/kLOC) than int8 (0.17).

Known errors shown on the card itself: in a French message that asks how to reset the printer password, the word for "printer" is tagged as a password with score 0.92, i.e. the model tags the noun after "password of the ...". A commit SHA and a request UUID in the same line are correctly ignored; `password: changeme  # put your own here` is correctly ignored (placeholder). These are good regression cases for piifence's "ordinary phrases" false positives.

Training data recipe (from the dataset card; the generator code is NOT in the GitHub repo). `templates.jsonl`: chat messages and technical snippets written by an LLM (gemma-4-E2B) with typed placeholders, filled by code with real-format fake secrets. `configs.jsonl`: framework config files generated by code (WordPress, Laravel, Django, Rails, Spring, docker-compose...), 20% with placeholders only (negatives). `chat_phrases.jsonl`: sentences naming a service after "password" with or without a value, inserted into real WildChat messages (the "password talk without a value" hard negative). `http.jsonl`: HTTP requests, responses, access logs, HAR-like entries, mostly without secret. `json.jsonl`: chat and template texts serialised as JSON with and without secret. `negatives.jsonl`: punctuation-dense non-secret code: byte arrays, URL-encoded strings, base64 images, hashes, minified JS. Also trained on CredData (Apache 2.0) and, from v1.1, on docs and sources of third-party npm packages as negatives (cut identifier FPs like camelCase function names, CSS values and words after an escaped `\n`). For the eval set the password base words and provider names were deliberately disjoint from training, and Telegram and Hugging Face token formats were never generated for training: a clean way to measure "unknown provider" generalisation.

Evaluation sets (HF `apartejs/aparte-secrets-gold`, ODC-BY 1.0, NOT in the GitHub repo, which holds no secrets even fake ones): `chat-fresh` 440 texts (default), `chat-fresh-json` 440, `gold` 775 dev texts (chat, code snippets, framework configs). JSONL rows: `id, lang, group (chat_fr|chat_en|code|framework), mode, text, secrets[{start,end,text,subtype,family}], decoys[...]`. The `decoys` field lists look-alike non-secrets present in the text (UUIDs, commit SHAs, IBANs, example keys, masked values), so it can score piifence's false positives per decoy family, not just per document. Offsets are Python code-point indices (piifence is Rust: convert from char indices, not bytes). `score.py` and `clean_repos.py` ship in the dataset repo. This is the most directly usable outside test for piifence's chat-side leaks (passwords in prose, French) and for the JSON-escaped shape.

## 7. DeepPass2 (SpecterOps): regex, then XLM-RoBERTa, then LLM verification

Sources: `SpecterOps/DeepPass2/deeppass2.py`, `.../utils/BERTprocessor.py`, `.../utils/finetune-BERT-chunked.py`, `.../utils/regexRules.jsonl`, `.../utils/trainingEvaluator.py`, `.../test/testDeeppass2.py`, card `hf:gneeraj/deeppass2-bert`.

Architecture: xlm-roberta-base (about 278M params, 512 tokens) fine-tuned with LoRA (r=64, alpha=128, dropout 0.05, targets query/key/value/dense), 2 labels (credential token vs not), plain argmax per token, no BIO and no subtypes. Python + Flask + transformers. License Apache 2.0 (repo); weights on HF are gated ("request access"). No speed numbers published. Pipeline (`scan_secret()`): Nosey Parker regexes (183 rules in `regexRules.jsonl`) run first; every regex match is then deleted from the document (`remove_np_result` does `re.sub(re.escape(match), "", doc)`), the rest is chunked into random-length 300–512-token chunks with 10% overlap ("That's what our model is trained on"), BERT tags tokens, and each chunk with hits is sent to an LLM with a prompt that asks it to confirm and return credentials inside `<credential></credential>` tags.

Span reconstruction (`BERTprocessor.py`): consecutive label-1 tokens are concatenated; a new credential starts when `start > previous_end + 1`. Only the first 512 tokens of a chunk are seen (`truncation=True`). Weaknesses to avoid: the training labeler uses `doc.find(credential)`, so only the first occurrence of a value is labelled positive and any repeat is trained as negative (`finetune-BERT-chunked.py` `preprocess`), and tokens are labelled only if fully inside the span, so boundary tokens are dropped. My inference: this teaches the model to miss repeated values, the opposite of what piifence wants.

Published numbers (card, on its own 2,200-chunk synthetic test split): chunk strict accuracy 86.67% (all passwords exact), overlap accuracy 97.72% (>30% overlap); password-level TP 1,201, FP 49, FN 138, recall 89.7%; with LLM stage strict 85.79%, overlap 95.35% (LLM slightly lowers recall). Not comparable to anything external.

Training data recipe (card; dataset not published): 2,000 LLM-generated long documents (emails, technical docs, logs, configs, 2000+ tokens), 50% with passwords; chunked at random boundaries into 300–400 tokens; passwords injected via skeleton sentences such as "Your account has been created with username: {user} and password: {pass}"; password values from CrackStation's "real human" breached password list plus LLM-made passwords and structured tokens; class balance kept realistic (<0.3% of tokens positive). Reusable idea: real human-chosen passwords (dictionary words, leetspeak, short upper-case strings) are the right source for piifence's "plain-word passphrase" and "upper-case short password" leaks; random-charset generators under-represent them. Card admits the model "tends to flag alphanumeric strings more readily than common words used as passwords".

Rules worth borrowing from `regexRules.jsonl` (Nosey Parker-derived). Prose password rules: `the (default )?password is '...'` / `"..."` with restrictive first char `[^'\n\#$|"{<+ ()\\]` and length 3–60 (np.generic.11/12), and `the (default )?password for (the )?(user|username) '...' is '...'` (np.generic.13/14). Quoted password assignment (np.generic.5/6): `password["']?[ \t]*(=|:|:=|=>)[ \t]*"([^$<%@.,\s+'"(){}&/\#\-][^\s+'"(){}/]{4,})"` — the first-char exclusion set is a cheap placeholder/interpolation filter (`$VAR`, `<pass>`, `%s`, `@param`, `{x}`). `Generic Secret` (np.generic.1): `secret.{0,20}\b([0-9a-z]{32,64})\b` case-insensitive, i.e. a 32–64 alnum within 20 chars after "secret" — relevant to piifence's 32-hex leaks when the keyword is within 20 chars (also matches "## Webhook secret" headings if the value follows within 20 chars, which is NOT the case for a value on the next line after a heading of normal length; my inference). Also `netrc` (`machine ... login ... password ...`), Postgres URI credentials, `Authorization: Basic <b64>`, .NET `NetworkCredential`, PsExec `-p`, Connect-VIServer. Note that Nosey Parker rules also flag password hashes (md5crypt, bcrypt, sha256crypt, sha512crypt, Cisco PBKDF2, Kerberos AS-REP) as findings, which is the opposite policy from piifence's hash guard; decide explicitly whether crypt-format hashes (`$2b$...`, `$6$...`) should be masked (they are crackable credentials).

Ensemble idea: regex first, remove regex hits from the text, then run the model on the remainder so known formats never reach the model and the model's FP budget is spent on free-form text; then an LLM verifier for precision. For piifence the LLM verifier is not an option (it would send the secret off-box) unless it is a local model.

## 8. Valendra Privacy Filter Mini: Qwen3-0.6B token classifier with a SECRET label

Sources: `valendra-tech/valendra-privacy-filter/README.md`, `.../docs/data-policy.md`, `.../configs/nemotron-labels.yaml`, `.../src/valendra_privacy_filter/datasets/synthetic.py`, `.../src/valendra_privacy_filter/inference/detector.py`, `.../examples/candle-wasm/src/decode.rs`, `.../experiments/interim-validation-checkpoint3000.json`, card `hf:valendra/privacy-filter-mini`.

Architecture: full fine-tune of Qwen3-0.6B-Base (causal attention baseline; a bidirectional-attention variant is an experiment) with a 41-label BIOES head over 10 categories (PERSON, EMAIL, PHONE, ADDRESS, GOVERNMENT_ID, FINANCIAL_ID, SECRET, IP_ADDRESS, DATE_OF_BIRTH, URL). FP32 safetensors about 2.38 GB, not quantized. 512-token windows, 64-token overlap, logits averaged on shared tokens, one global constrained Viterbi path. Output: char spans with type and an uncalibrated score (geometric mean of token probabilities, optional temperature). Apache 2.0 (code, model; Qwen base Apache 2.0); training data OpenPII 1M and Nemotron-PII, both CC BY 4.0. English and Spanish. There is a Rust/Candle WASM port (`examples/candle-wasm/src/decode.rs`) with constrained Viterbi and the secret reconciliation in Rust, directly readable for piifence (Rust).

Speed: CPU p50 106 ms per document on an Apple M5 CPU (FP32), 100 synthetic validation docs (README). Too large for piifence's hot path in my view (2.4 GB FP32, 0.6B params, 2–3x slower than a 32M ModernBERT would be; inference).

Published numbers: full synthetic test split (22,262 docs) untyped exact-span P/R/F1 0.805/0.905/0.852; challenge split (14,461 docs) F1 0.620 vs OpenAI Privacy Filter 0.702. Per-category SECRET on the 100-doc interim validation: TP 22, FP 7, FN 1 (P 0.76, R 0.96) — tiny sample. Each test split has only two clean negative documents, so no usable FP rate. SECRET training data is weak for piifence: Nemotron `api_key`, `password`, `http_cookie`, `cvv`, `pin` map to SECRET (`configs/nemotron-labels.yaml`), and project synthetic secrets are literal shapes like `SYNTHETIC_TEST_KEY_<8 digits>`, `sk_test_SYNTHETIC_<8 digits>`, `NOT_A_REAL_PASSWORD_<8 digits>` (`synthetic.py`), labelled positive "when presented as credentials". Not a candidate model for piifence; useful only for its decoder ideas and its negative-template ideas.

Post-processing ideas (`detector.py`, README line 207). (1) Adjacent-fragment reconciliation: when adjacent spans of different types cover one whole word and one is SECRET, rescore the whole word as each type and merge to SECRET only if that path's summed log-prob is strictly higher. (2) Whitespace-run growth (`_extend_secrets_to_whitespace_runs`): take a SECRET fragment, grow it to its whitespace-delimited run, strip wrapping `"'«“‘([{<` and trailing `"'»”’)]}>.,;:`, score the run as `S` or `B I... E` SECRET and replace the fragments only when that score beats both "all O" and every other category. The docstring cites credentials with symbols where the model tags only part (e.g. a `ghp_` prefix or a word+year+symbol password). This is a principled, model-gated version of span extension piifence could add for partial hits (e.g. upper-case short passwords where the tokenizer splits mid-run). (3) Overlaps resolved by confidence with deterministic tie-breaking; redaction applied right to left.

Data policy ideas: split train/val/test by a hash of the template after replacing annotated values with their labels (prevents template leakage); remove cross-split duplicates by hashing high-signal values (secrets of at least 8 normalized chars) in memory. Negatives explicitly include placeholders (`${EMAIL}`, `YOUR_API_KEY`), documentation IPs/emails (192.0.2.x, 203.0.113.x, example.com), company names, version and build numbers, a short hex "hash" next to a version number, bibliographic references. A secret nested inside a URL query (`?token=...`) is labelled SECRET inside a URL span — the same shape as piifence's "password in a neutral URL query param" leak, but here the param name is `token`, not neutral.
