# CredSweeper + CredData: findings for piifence

Sources (read-only): `Samsung/CredSweeper` (v1.19.6, HEAD 4482593f, MIT) and `Samsung/CredData` (HEAD 5b6db1a2, Apache-2.0 for the metadata; downloaded files keep their original repo licenses). Paths below are relative to those repos: `CS/` = CredSweeper, `CD/` = CredData. Nothing was run from either repo. Where I say "inference" it is my reading, not something stated in the source.

## 0. Top takeaways (ordered by usefulness to piifence)

1. **Structured data becomes `key = value` lines for the keyword rules.** JSON/YAML/CSV get parsed, and every `(key, value)` pair whose key contains a secret keyword is turned into a synthetic line `f"{key} = {repr(value)}"` and run back through the normal keyword rules (`CS/credsweeper/deep_scanner/abstract_scanner.py:205-299`). They also pair sibling fields: `{"key": "api_key", "value": "..."}` is treated as `api_key = "..."` (`key_value_combination`, lines 123-147, checks the field names `key/KEY/Key` and `value/VALUE/Value`). CSV is parsed with the header row as the keys (`CS/credsweeper/deep_scanner/csv_scanner.py`), so a UUID in a column called `api_key` gets keyword context. **For piifence:** (a) add `name`/`Name` + `value`/`Value` sibling pairing (k8s env, AWS tags, GitHub/Terraform settings) to the key rule. That is the direct fix for "password under JSON `name` key". (b) Turn markdown and pipe tables in tool output into `header = cell` pairs before running the key rule. That fixes "UUID API key in a table column". (c) Inference: do the same with a markdown heading (`## Webhook secret`) as the key for the first non-empty line or code block under it.
2. **Prose ("doc") rules allow linking words between keyword and value, plus a mixed-character-class requirement on the value.** `DOC_CREDENTIALS` allows `\s+(?i:is|are|was|were)(\s*[:-])?\s+` as the separator. `PASSWD_PAIR`/`SECRET_PAIR`/`ID_PASSWD_PAIR` only accept a value that has at least one upper-case letter, one lower-case letter and one digit or symbol, using regex conditionals (`(?-i:(?P<a>[A-Z])|(?P<b>[a-z])|(?P<c>[0-9/_+=~!@#$%^&*;:?-])){8,64}(?(a)(?(b)(?(c)...|(?!x)x)|(?!x)x)|(?!x)x)`, `CS/credsweeper/rules/config.yaml:69-192`). They support Korean keywords (`비밀번호|비번|패스워드|암호|토큰|키`), the Korean separator `설정은` and the topic particles `는/은`. **For piifence:** copy the structure for Russian (`пароль|пароля|паролем|токен|ключ|секрет|логин`, separators `—`, `:`, `это`, `такой`). Also allow up to about 6 words between the keyword and `is`/`:`, because CredSweeper does not handle "The wifi password for the office is X". Use a 2-of-3 class rule (or upper+digit) so all-caps values like a 10-char `[A-Z0-9]` password qualify. CredSweeper's strict 3-of-3 rule would miss that case too.
3. **Left-boundary regex that tolerates escapes, URL encoding and ANSI colour codes.** Every prefix-based token rule starts with `(?:^|/|[^\\0-9A-Za-z+_-]|\\[0abfnrtv]|(?:%|\\x)[0-9A-Fa-f]{2}|\\[0-7]{3}|\\[Uu][0-9A-Fa-f]{4}|\x1B\[[0-9;]{0,80}m)(?P<value>...)` and ends with `(?![0-9A-Za-z_+-])` (e.g. `config.yaml` "UUID", "Dropbox App secret", "Hashicorp Vault Token"). **For piifence:** Bash tool output often has ANSI colour codes, JSON-escaped `\n`, `\u00xx` and `%xx` right next to a token. Use the same prefix in our gitleaks custom rules and Rust guards so a token right after `\n`, `%3D` or `\x1b[32m` still matches.
4. **URL handling.** The keyword regex accepts encoded separators `%3d`, `\u003d`, `=&gt;`, `%26gt;` and encoded quotes `&quot;`, `&apos;`, `&#34;`, `&#39;`, `\u0022`-style (`CS/credsweeper/common/keyword_pattern.py`). When a value sits in a URL, `LineData.clean_url_parameters()` takes the variable as the part after the last `&`/`?`/`;` and cuts the value at `&`, `;`, `#`, `\u0026`-style escapes and (when the separator was `%3D`) at `%26` and similar (`CS/credsweeper/credentials/line_data.py`, `url_percent_split`, `check_url_part`). They never URL-decode the value (no `unquote` anywhere). **For piifence:** our "neutral param" leak (`?u=admin&p=<pw>`) is not covered by CredSweeper either: its Password keyword is `(?<!by)pass(?!e[dns]|ing|ion|age|\s+[a-z]{3,80})|(?<!pro|sto)p(s|ss|as)?w(o?r)?d(?!ump)|pswr?\b|(\b|_)pw(_|\b)`, so a lone `p` does not match. Inference/suggestion: an "ID+password pair" rule for query strings. If a query has a user-like param (`u|user|username|login|email|account`), treat a sibling 1-2 letter param (`p|pw|pwd|pass|k`) as a password. This mirrors their `ID_PAIR_PASSWD_PAIR` doc rule (variable `id|login|account|root|admin|user|name|wifi|role|host|default`). Also URL-decode query values before running the model and guards, and map spans back to the encoded text.
5. **Recursive base64 decode-and-rescan.** `EncoderScanner` (`CS/credsweeper/deep_scanner/encoder_scanner.py`) matches any blob of at least 12 chars that has upper, lower and digit/`+/` (or `-_`) via regex conditionals. It strips whitespace and backslashes, base64-decodes it (padding-tolerant, URL-safe auto-detect, `Util.decode_base64`, `CS/credsweeper/utils/util.py:419`), and rescans the decoded bytes with the full scanner (the `|BASE64` info tag). `ValueBasicAuthCheck` keeps `Basic <b64>` only if it decodes to `login:password`. **For piifence:** decode base64 candidates of 12 to about 4k chars once. Rescan if the decoded bytes are printable UTF-8, and mask the whole encoded span if anything is found inside. Do the same for hex runs whose length is even and that decode to printable ASCII. This covers our base64/hex-encoded leak. CredSweeper has no hex decoding (`fromhex` only appears in the Grafana checksum filter).
6. **Filters for base64 data dumps (our image-data FPs).** (a) `ValueBase64PartCheck`: drops a candidate that is part of a longer base64 run. It fires when the char just before or after the value is one of `/ + \ %`, or the value starts at column 0 and the line is at least twice the value's length. It then compares Shannon entropy of the left part, the value and the right part (mean − 1.1·stdev). (b) `ValueNotPartEncodedCheck`: drops it if the previous line matches `(^|[^A-Za-z0-9]+)(?P<val>(([A-Za-z0-9_-]{4}){16,64})|(([A-Za-z0-9+/]{4}){16,64}))([^=A-Za-z0-9+/|_-]+|$)` (a 64-256-char base64 line), or the next line matches the `{4,64}` variant. In other words, a candidate inside a wrapped base64 block. (c) `ValueBase64DataCheck`: base64-decodes the value. If the decoded bytes are all ASCII (or under 9 bytes), it is encoded text and not a key, so drop it. If the value lacks any of digits, lower or upper case, drop it. (d) `LineGitBinaryCheck` (base85 git binary-patch lines) and `LineUUEPartCheck` (`^M[!-\`]{60}$` uuencode lines). Inference: add the magic prefixes `iVBORw0KGgo` (PNG), `/9j/` (JPEG), `R0lGOD` (GIF), `UklGR` (WEBP), `JVBERi0` (PDF) and `data:[a-z]+/[a-z0-9.+-]+;base64,` as a hard "not a secret" guard. Anthropic `image`/`document` content blocks with `source.type == "base64"` should never be scanned.
7. **Cheap "is it random?" tests, tuned per charset and length** (Section 4). These are min-entropy curves for base64/base32/base36 and a keyboard-hop statistic (`HopStat`) that rejects keyboard walks and natural text. Both are a few lines of Rust each and useful as a pre-filter on model spans.
8. **Structural validators that confirm a true positive** (checksums). These are GitHub `gh?_`/`npm_` CRC32 in base62 over the body (`value_github_check.py`), Atlassian/Bitbucket `ATBB…` CRC32 hex suffix and `integer:bytes` base64 payload, Cloudflare `cfk_/cfat_/cfut_` CRC32, Grafana service-account CRC32 suffix, Grafana `glc_` base64 JSON with keys `o,n,k,m`, JWT (header and payload JSON keys from the IANA lists plus a high-entropy signature), Azure tokens (header `alg,typ,kid`, payload `iss,exp,iat`), JWK (`"kty"` plus private parts `d`/`k`), bech32 (`AGE-SECRET-KEY-1`), and base64-encoded PEM. These let us mask with high confidence even when there is no keyword, and drop look-alikes that fail the checksum.

## 1. Mapping to piifence's measured weak spots

### Leaks

- **32-hex with no keyword nearby.** CredSweeper does not catch this either. There is no keyword-free generic hex rule. `ValueNumberCheck` drops `^(0x)?[0-9a-f]{1,128}[ul]{0,3}$` only when the length is under 22, so it treats short hex as numbers and long hex as a possible key. Their only signal is context: the ML line input (±64 chars around the value) plus hash markers. Inference: entropy cannot separate a 32-hex key from an MD5. Use context words in a window instead. Hash cues: `md5|sha\d*|digest|checksum|etag|commit|integrity|hash|fingerprint|thumbprint|object id|blob|tree`, a git-log or `ls`-like layout, or a path or filename right after it. Key cues are the keyword list below. Default to masking 32/40/64-hex only when a key cue is within N lines (see next item).
- **Hint on the previous line in prose.** CredSweeper has no general "keyword on previous line" logic. Keyword rules and the ML model see one line only (ML `line_input` is the stripped line, cut to 128 chars around the value, `CS/credsweeper/ml_model/ml_validator.py:encode_line`). The reusable mechanism is `MultiPattern.get_line_positions` (`CS/credsweeper/scanner/scan_type/multi_pattern.py`). It searches ±10 lines with priority: same line first, then forward and backward lines in alternating order, with a penalty for crossing `{`/`}` scopes. It is used for AWS key-id + secret pairs. Suggestion (inference): when a line is a bare high-entropy token (the line is only the token, maybe in backticks or a code fence), look back 1-3 lines for a secret keyword (`token|key|secret|password|credential|api|passphrase` plus Russian forms) and treat a hit as key-rule context.
- **UUID API key in a table column or under a `## Webhook secret` heading.** See takeaway 1 (CSV header → key). CredSweeper's `UUID` rule (`config.yaml:194`) reports every UUID with severity `info`, `use_ml: false`, and only `ValuePatternCheck(4)` as a filter. CredData labels 2,539 UUID lines True vs 3,716 False, so UUID keys are common in real repos. A UUID alone carries no signal; context is everything.
- **Password under a JSON `name` key.** See takeaway 1. Extend sibling pairing to `name`/`value`, `Name`/`Value`, `key`/`value`, `id`/`secret`, `parameter`/`value` (inference for the extra pairs; CredSweeper only does `key`/`value`).
- **Token used as a host label.** Only covered for known shapes: Firebase `*.firebaseio.com` / `*.firebaseapp.com`, S3 `*.s3.amazonaws.com`, Slack webhooks. `URL Credentials` handles `scheme://user:pass@host` with the regex `(?P<variable>[+0-9A-Za-z-]{2,80}://)([^\s'"<>\[\]^~\`{|}:/]{0,80}:){1,3}(?P<value>[^\s'"<>\[\]^~\`{|}@:/]{3,80})@` and its own filter group (`UrlCredentialsGroup`, which leaves out variable-name-based filters). Nothing generic for a random subdomain label. Inference: apply the base64/base36 randomness tests to each DNS label of length 20 or more.
- **Plain-word passphrases.** CredSweeper deliberately **drops** these. `ValueSplitKeywordCheck` drops a value if any whitespace-separated word is in `keyword_checklist.txt` (977 common code and English words). `ValueDictionaryKeywordCheck` drops it if dictionary words cover at least 1/3 of it (`scrap_len < 2*replaced_len`). `ValueTokenCheck` drops an unquoted value whose first space-separated token is under 5 chars. CredData's obfuscation also replaces word-like passwords with random characters (Section 6), so the benchmark barely tests passphrases. **For piifence:** keep word filters off when the keyword context is strong (`password is ...`, `passphrase:`), and only apply them to keyword-free model spans.
- **Russian prose.** No Cyrillic support (grep for `пароль` finds nothing). Copy the Korean extension pattern from the doc rules (takeaway 2).
- **Secrets split across messages.** Nothing relevant. CredSweeper is file- and line-oriented; multi-line search stays inside one file.
- **Upper-case short passwords.** Missed by `PASSWD_PAIR` (needs a lower-case letter) and by `DOC_CREDENTIALS` (the keyword must be followed directly by `is`/`:`; "password for the office is" breaks it). See takeaway 2.
- **URL-encoded, base64 or hex secrets.** See takeaways 3-5.

### False positives (what CredSweeper does)

- **Hashes and digests.** These are ML features, not hard filters. Value pattern "SHA marker" `(?i:sha)[_-]?(224|256|384|512)`. Variable pattern `(?i:( h1$|md5|sha[_-]?(224|256|384|512)))`. Variable-ends-with list `(?i:(icon|label|mode|field|format|number|sum|size|len(gth)?|name|type|manager|algorithm|pattern|view|error|date(time)?|time(stamp)?|tag|version|hash|rate|code|fingerprint)s?$)`. Variable words `hash`, `fingerprint`, `thumbprint`, `md5`, `sha`, `crypt`, `encrypt`, `decrypt` (`CS/credsweeper/ml_model/ml_config.json`). Hard filter: `ValueHexNumberCheck` `^0x[0-9a-f]{1,16}$`. Labelling rule 5 in CredData: package or resource version hashes (`integrity sha512-…`) are False. Suggestion: also make the key-name blocklist in our key rule match these variable-name suffixes.
- **IDs.** Variable pattern `(guid|[^a-z](?i:u?id)|([^A-Z](G?U)?I[dD])s?)$`, plus `keyid`, `key_id`, `guid` in the variable word list. Value pattern for an AWS key ID `^A[0-9A-Z]{19,20}$` (an ID, not a secret). Key-rule exclusions `(?i:(?:uniq(?:ue)?|escap(?:e|ing)|resources?|projects?|filters?|pub(?:lic)?)_?keys?)`, and the `Key` keyword itself is `key(?!word|board|pad|name)`.
- **Variable names and code identifiers.** `ValueCamelCaseCheck`: an unquoted value matching `[a-z]+([A-Z][a-z]+)+|[A-Z][a-z]+([A-Z][a-z]+)+` that contains 2 or more morphemes from `morpheme_checklist.txt` (1,605 subword fragments) is dropped. ML features add camel `^[a-z][a-z]{1,16}[0-9]*([A-Z]([a-z]{1,16}[0-9]*|[0-9]{1,16})){1,8}$`, Pascal `^([A-Z]([a-z]{1,16}[0-9]*|[0-9]{1,16})){1,8}$`, UPPER_SNAKE `^(_+[0-9]{1,16}|_*[A-Z]{1,16}[0-9]*)(_+([0-9]{1,16}|[A-Z]{1,16}[0-9]*)){1,8}_*$` and lower_snake. `ValueSimilarityCheck`: drops if the value is a substring of the variable (or the reverse when the variable has at least 4 chars), or if `SequenceMatcher(variable, value).ratio() > 0.75`. `ValueMethodCheck`: drops an unquoted value containing `function` or matching `^[~.\->:0-9A-Za-z_]+\(.*\)`. `ValueArrayDictionaryCheck`: drops `\[['"]?[^,]+['"]?]` and values wrapped in `[`/`(`. `ValueStringTypeCheck`: in `.py/.js/.ts/.java/.go/...`, an unquoted value after `=` (that is not a comment, not a number, not a byte list) is code, so drop it. `ValueAllowlistCheck` (templating, placeholders): `ENC\(.*\)`, `ENC\[.*\]`, `\$\{(\*|[0-9]+|[a-z_].*)\}`, `\$[0-9]+(\s|$)`, `#\{.+\}`, `\{\{.+\}\}`, quoted `\$[a-z_][0-9a-z_]+((::|->|\.)[a-z_]|\[|$)`, `\$\([^)]+\)`, `.*\*\*\*` (masked), and unquoted `[~a-z0-9_]+((\.|->)[a-z0-9_]+)+\(.*$` (method chain). `ValueFilePathCheck`: unix and windows path heuristics combined with a morpheme count.
- **Ordinary phrases.** `ValueBlocklistCheck` drops the value when `true|false|null|none|bearer|string|value|undefined|uuid` makes up 70% or more of it. `ValueMorphemesCheck` counts morphemes with a threshold of `max(1, len(value).bit_length() - 4)`. The `MorphemeDense` ML feature is total morpheme length / value length. `ValueTokenCheck`, `ValueSplitKeywordCheck` and `ValueDictionaryKeywordCheck` are described above. `ValueLastWordCheck` drops values under 16 chars that end with `:`. `ValuePatternCheck` drops values with 4 or more identical, ascending or descending chars (dynamic length = `max(4, len.bit_length())`, also checked on even/odd interleaved characters). Placeholders: the ML value-word list includes `changeme, example, fake, mock, test, xxx, xyz, abc, aaaa, asdf, foo, bar, redacted, my, nil, 123, 141592653 (pi), 718281828 (e)`. `LineSpecificKeyCheck` drops pattern hits within ±64 chars of `example|\benc[\(\[]|\btrue\b|\bfalse\b`.
- **App-ID listings.** Nothing specific. Their nearest equivalent is the "variable ends with id/name/type/code" rule plus `Tencent WeChat API App ID` being a separate info-level rule. Inference: a run of 3 or more similar-shape tokens in a list or table under an `id`/`app`/`client` header is a listing of identifiers, not secrets.

## 2. CredSweeper pipeline

- **Line pre-gate** (`CS/credsweeper/scanner/scanner.py:138-176`). Keyword rules only run on lines at least `min_keyword_len` long that contain `=`, `:`, `define`, `%global`, `set`, `%3d`, `\u003d` or `<<<`. Each rule has `min_line_len` and `required_substrings` (cheap substring prefilter) and/or `required_regex` (e.g. `[0-9A-Za-z_-]{15}`). The `target: code|doc` field decides which rule set runs. `--doc` enables only the doc rules (DOC_GET, DOC_CREDENTIALS, SECRET_PAIR, PASSWD_PAIR, IP_ID_PASSWORD_TRIPLE, ID_PAIR_PASSWD_PAIR, ID_PASSWD_PAIR) plus the pattern rules marked `doc`. Long lines are chunked: `MAX_LINE_LENGTH = 8000`, `CHUNK_SIZE = 4000`, `OVERLAP_SIZE = 1000` (`CS/credsweeper/common/constants.py:136-146`). Minimum value length is 4.
- **Rule types.** There are 153 rules in `CS/credsweeper/rules/config.yaml`. `pattern` rules are prefix or shape regexes for vendors (Anthropic `sk-ant-(api|admin)0[1-4]-[0-9A-Za-z_-]{64,128}`, OpenAI, GitHub, Slack, JWT, PEM, and so on). `keyword` rules (`API`, `Auth`, `Credential`, `Key`, `Nonce`, `Password`, `Salt`, `Secret`, `Token`) use the generic variable-separator-value template. `multi` rules need a second pattern within ±10 lines. `pem_key` rules detect multi-line PEM. Keyword regexes: `api(?!tal)`, `auth(?!ors?(?!i[tz]))`, `credential`, `key(?!word|board|pad|name)`, `(?<!\\)nonce`, the Password regex quoted above, `salt`, `secret`, `token(?!ize)`.
- **Keyword template** (`CS/credsweeper/common/keyword_pattern.py`). The pieces are `directive` (`#define`, `set(`), `key_left`, `(?P<keyword>…)`, `key_right` (up to 80 non-separator chars, so `db_password_prod` works), `separator`, optional `wrap` (`new String(`, `os.getenv("X", `, `dict.get('x', `), `string_prefix` (`b r u f @`…), optional quote (including `&quot;` and backslash-escaped quotes), optional `auth_keywords` (`oauth|bot|basic|bearer|apikey|accesskey|ssws|ntlm|token`), then `value` and `right_quote`. Separators: `:=`, `:` (not `::`), `=>`, `=&gt;`, `!==`, `!=`, `===`, `==`, `=~`, `=`, `<<<`, `%3d`, `\u003d`. Flags are IGNORECASE and DOTALL. Value: 4-8000 chars, quote-aware. Unquoted values stop at whitespace, quotes, `,`, `;` and `\`. For a `wrap` without quotes the value must be 16 chars or more.
- **Value sanitising** (`line_data.py`). Curly quotes (U+2018..U+201F) are stripped as quote pairs, and URL query, bash params, TOML brackets and closing tags are cleaned off. `is_well_quoted_value` (matching quotes) is a key signal: many filters skip quoted values, so a quoted value is more trusted.
- **Filter groups** (`CS/credsweeper/filters/group/`). `GeneralKeyword` (API, Auth, Credential, Key, Nonce, Salt, Secret, Token): `ValueAllowlistCheck, ValueArrayDictionaryCheck, ValueBlocklistCheck, ValueCamelCaseCheck, ValueFilePathCheck, ValueHexNumberCheck, ValueLastWordCheck, ValueMethodCheck, ValueSimilarityCheck, ValueStringTypeCheck, ValueTokenCheck`, plus (when not in doc mode) `ValuePatternCheck, ValueNotAllowedPatternCheck`, plus `ValueDictionaryKeywordCheck, ValueSealedSecretCheck`. `PasswordKeyword` is the same base plus `ValueLengthCheck(max 64), ValueSplitKeywordCheck, ValueSealedSecretCheck, LineGitBinaryCheck, LineUUEPartCheck`. `UrlCredentialsGroup` is the base without the variable-dependent filters, with max length 80. `TokenPattern` (vendor-prefix tokens) is `ValueMorphemesCheck, ValueNumberCheck, ValueCamelCaseCheck, ValuePatternCheck`. `WeirdBase64Token` is `ValueMorphemesCheck(1), ValueNumberCheck, ValueBase64DataCheck, ValueTokenBase64Check, ValueEntropyBase64Check, ValuePatternCheck, ValueNotPartEncodedCheck, ValueBase64PartCheck`. `WeirdBase36Token` is `ValueMorphemesCheck(1), ValuePatternCheck, ValueNumberCheck, ValueTokenBase36Check, ValueEntropyBase36Check`. `GeneralPattern` is `LineSpecificKeyCheck, ValuePatternCheck`.
- **Remaining filters, one line each.** `ValueNotAllowedPatternCheck`: an unquoted value ending in `[<>\[\]{}]\s+`, `&gt;`, or starting with `\` or `\n`. `ValueSealedSecretCheck`: drops Bitnami SealedSecret ciphertext (`Ag…` over 700 chars or `AQ…` over 350 chars, with `SealedSecret`, `encryptedData` and `bitnami` within ±100 lines). `ValueSearchCheck`: helper for multi rules. `ValueBase32DataCheck`: base32 decode, drop if the result is ASCII or low entropy. `ValueBase64KeyCheck` / `ValueBase64EncodedPem`: keep only if the value decodes to a loadable private key. `ValueDiscordBotCheck`: first part base64-decodes to an integer of at least 1000, rest passes entropy. `ValueJfrogTokenCheck`: `cmVmdGtuO` decodes to `reftkn:\d+:\d+:`, or `AKCp` base58-decodes to 54 bytes. Filters return True to mean "drop".
- **Rules + ML combination** (`CS/credsweeper/app.py:466-501`). Duplicates are purged, then candidates are grouped by (path, line, value). If any candidate in a group has `use_ml: true`, the whole group goes to the model. A group below the threshold drops only its `use_ml` candidates; `use_ml: false` candidates in the same group stay. ML is used on the keyword rules, doc rules, URL credentials, CURL/CMD/SQL password and Bearer. Vendor-prefix rules mostly skip ML and rely on filters and checksums. The ML step is a **post-filter on rule candidates, not a span finder.**

## 3. CredSweeper ML model

- **Architecture** (`CS/experiment/ml_model.py`, Keras, exported to ONNX `CS/credsweeper/ml_model/ml_model.onnx`, 11.5 MB). Three character-level BiLSTMs over one-hot input: `line_input` is the stripped line, up to 128 chars centred on the value; `variable_input` is up to 64 chars; `value_input` is up to 64 chars. The character set is ASCII printable plus ESC (`\x1b`); unknown chars map to a FAKE slot and padding to ZERO. LSTM units equal the sequence length. The branches are concatenated with a hand-feature vector that goes through a softmax "attention" Dense layer and is multiplied back. Then come two ReLU Dense layers of width `2*128 + 2*2*64 + n_features` with dropout 0.21/0.23 and a sigmoid output. Loss is binary cross-entropy with balanced class weights. Dropout hyperparameters are in `CS/experiment/hyperparameters.py`.
- **Hand features** (`CS/credsweeper/ml_model/ml_config.json`). RuleSeverity. EntropyEvaluation: Rényi α=0.5, Shannon and Rényi α=2, each divided by log2(len), plus 14 one-hot "charset ⊆ {hex, UUID upper/lower, base16 upper/lower, base32, base36, base62, base64url(pad), base64std(pad), ascii-visible, printable}" flags. Lengths of line, variable and value. Regex flags: bash var, comment prefix, `<placeholder>`, repeated-pair `(?:(\S)(\S))((\1.)|(.\2)){7,}`, SHA marker, ASN.1 `\b(MII|LS0t)`, camel/Pascal/UPPER/lower naming, variable-not-allowed, hash-in-variable, ID-in-variable, AWS key ID, UUID `^(?i:[0-9a-f]{8}(-[0-9a-f]{4}){3}-[0-9a-f]{12})$`, key-rule exclusion, variable-ends-with words, `$PWD`. Word-in lists for the variable, the value, the preamble (up to 64 chars before the variable), the transition (between variable and value: `basic`, `bearer`, `get`, `env`, quotes and so on) and the postamble. Word-in-path. MorphemeDense. HasHtmlTag. IsSecretNumeric. FileExtension one-hot (about 180 extensions). RuleName one-hot (16 rules), ORed across the group.
- **Thresholds.** Presets in `ml_config.json` are lowest 0.229, low 0.357, medium 0.622 (default), high 0.798, highest 0.930.
- **Training.** Done on CredData through `CS/experiment/` with a random 85/15 row-level `train_test_split` (`train.py:95`). This is not split by repository, so test rows share files and repos with training rows (inference: optimistic metrics).
- **Relevance to piifence.** Their model is a binary validator for regex candidates, using variable/value/line context. Ours is a token classifier. The transferable idea is the **feature set**: charset one-hots, entropy normalised by log2(len), naming-style regexes and the preamble/transition word lists. These would make a cheap second-stage scorer for our model spans (e.g. a logistic or GBDT model in Rust over the same features), trained on our own FP/FN corpus. Inference.

## 4. Entropy and randomness thresholds (copyable)

- **Shannon entropy** is computed per character over the value (`Util.get_shannon_entropy`).
- **Base64 minimum entropy for length x** (`value_entropy_base64_check.py`). 12 ≤ x < 18: `0.915*log2(x) - 0.047`. 18 ≤ x < 35: `0.767*log2(x) + 0.5677`. 35 ≤ x < 65: `0.944*log2(x) - 0.009*x - 0.04`. 65 ≤ x < 256: `0.621*log2(x) - 0.003*x + 1.54`. x ≥ 256: `6 - 64/x`. Below 12 the minimum is 0, which means "always reject". Examples: x=16 gives about 3.61, x=32 about 4.40, x=40 about 4.62.
- **Base32** (`value_entropy_base32_check.py`). 8 ≤ x < 17: `0.80569*log2(x) + 0.13440`. 17 ≤ x < 33: `0.66350*log2(x) + 0.71144`. x ≥ 33: 4.04.
- **Base36** (`value_entropy_base36_check.py`). x == 15: 3.374. 10 ≤ x < 26: `0.73157*log2(x) + 0.47413`. x ≥ 26: 3.9.
- **HopStat keyboard test** (`CS/credsweeper/utils/hop_stat.py`, `value_token_base*_check.py`). Each char is mapped to QWERTY axial hex-grid coordinates (shifted symbols map to their base key, case-folded). Then mean and stdev of the hop distance between consecutive chars are computed. For a value of exactly length n ∈ {8, 10, 15, 16, 20, 24, 25, 32, 40, 50, 64} it must satisfy `mean_hop ∈ μ_h ± k·σ_h` and `stdev ∈ μ_d ± k·σ_d`; otherwise it is "not random". k ranges from 2.616 (n=8) down to 2.160 (n=64). The μ/σ tables are given per charset (base64, base36, base32). Example for base64, n=32: μ_h 3.762, σ_h 0.452, μ_d 2.243, σ_d 0.295, k 2.210. Lengths not in the table raise an exception and pass. Rejects keyboard walks and real words, which sit close together on the keyboard.
- **`Util.is_ascii_entropy_validate(bytes)`** answers "is this decoded blob text?" It returns True if the data is under 9 bytes or all bytes are under 0x80. Otherwise it applies a binned-entropy check against `MIN_DATA_ENTROPY` = {16: 1.67, 20: 2.08, 32: 3.25, 40: 3.65, 64: 4.58, 384: 7.39, 512: 7.55} (`CS/credsweeper/utils/util.py:82-145`). Use it after decoding base64: decoded ASCII means encoded text (rescan it); high-entropy bytes mean a key or binary.

## 5. Keyword and word lists worth importing

- **`CS/credsweeper/common/keyword_checklist.txt`**: 977 common English and code words of 3 or more letters (abort, about, access, account, action, …). Used as a "this value is made of words" detector. Useful for our ordinary-phrase and identifier FPs, but do not use it on strong password contexts.
- **`CS/credsweeper/common/morpheme_checklist.txt`**: 1,605 subword fragments (`_cfg`, `_env`, `acce`, `admi`, `auth`, `/usr`, digit runs like `000`, pi/e digit runs). Used for density and count thresholds against identifiers and paths.

## 6. CredData

- **What it is.** A line-level labelled benchmark over source repos. The README says 297 GitHub repos (chosen across 181 topics, stars filter, license filter), about 19.5M lines and 11,408 files. The current `CD/snapshot.json` has 337 repos at pinned commits. My count of `CD/meta/*.csv` (337 files) gives **67,897 labelled rows: 15,753 T, 48,061 F, 4,082 X**. The README's "73,842 labelled / 4,583 True" figures are stale. The CI file `CS/.ci/benchmark.txt` reports 17,020,109 lines, a markup of 64,797 items, 18,222 positives and 54,116 negatives.
- **How it was built and labelled.** Candidate lines were gathered by running several scanners (CredSweeper, credential-digger, detect-secrets, gitleaks, shhgit, truffleHog, truffleHog3, wraith) and grep-like filtering, then **manually reviewed**. T means it looks real. F is a false positive. X is test, example or placeholder; it is scored as negative. Ground rules (`CD/README.md`): values in test or example directories are **True**. Obvious placeholders `<YOUR_PASSWORD>` are False. Function calls and env references are False. Encoded data is True only if the decoded content is a credential. Package or resource hashes are False. File-type-aware quoting rules apply (an unquoted `password=x` is real in `.yaml` but not in `.py`). Locale files are False. An `example.com` marker means False for ML rules. To extend the dataset, the maintainers run CredSweeper with `--ml_threshold 0`, auto-insert its findings with `--fix`, then review. **So the markup is seeded by CredSweeper and biased toward what CredSweeper finds** (inference from the README steps).
- **Format.** One CSV per repo: `Id, FileID, Domain, RepoName, FilePath, LineStart, LineEnd, GroundTruth, ValueStart, ValueEnd, CryptographyKey, PredefinedPattern, Category`. `Category` holds colon-joined CredSweeper rule names (e.g. `Secret:Token`). `ValueStart`/`ValueEnd` are character offsets in the line; empty or -1 means the whole line (F only). 1,003 True rows have no value offsets and 1,351 rows span multiple lines (mostly PEM).
- **True rows by category** (my count; a row can have several). Key 4,328; Password 2,778; UUID 2,539; Secret 1,595; Auth 1,280; Token 1,208; PEM Private Key 1,193; Basic Authorization 692; Bearer Authorization 289; API 253; URL Credentials 228; AWS Client ID 213; JSON Web Token 182; Nonce 178; NTLM 126; Credential 96; AWS S3 Bucket 92; Salt 90; JWK 80; Dropbox App secret 74; PASERK 72; OTP/2FA 64; PASETO 63; NKEY 60. There are no `DOC_*` categories in the meta (the doc rules are mapped onto Password, Secret and so on).
- **True rows by extension** (T / total labelled). txt 5,242/10,959; json 1,821/11,980; go 1,470/7,467; yml 1,300/2,645; md 795/3,111; js 708/3,763; py 663/4,396. The large share of `.txt`/`.md`/`.yml` makes it fairly relevant to prose and config text in tool output.
- **Published results, original README table (April 2022, train and test combined).** CredSweeper P 0.917, R 0.808, F1 0.859 (TP 3,701, FP 337, FN 882). gitleaks P 0.526, R 0.244, F1 0.334. detect-secrets P 0.142, R 0.381, F1 0.206. truffleHog3 P 0.150, R 0.547, F1 0.235. wraith P 0.225, R 0.196, F1 0.209. credential-digger P 0.090, R 0.105, F1 0.096. shhgit P 0.519, R 0.072, F1 0.126. truffleHog (v2) P 0.25, R 0.009, F1 0.018.
- **Current CredSweeper CI result** (`CS/.ci/benchmark.txt`, default `credsweeper --path data`, medium threshold). TP 17,802, FP 161, FN 420: **P 0.991, R 0.977, F1 0.984**. Per rule: Password P 0.996/R 0.972. Key 0.990/0.989. Token 0.993/0.924. Secret 0.994/0.975. UUID 0.977/0.991. URL Credentials 0.996/0.978. Azure Access Token R 0.708. Dropbox App secret 0.897/0.703. OTP/2FA R 0.844. These scores are **in-sample**: the model is trained on the same data with a random row split, and the markup is seeded by CredSweeper. Treat them as an upper bound, not a fair comparison with gitleaks. No up-to-date numbers for other tools are in the repos.
- **Real or obfuscated?** `download_data.py` shallow-fetches each repo at the pinned commit and copies only the files named in the meta. A file is matched when `sha256(relpath)[:8] == FileID`; the repo id is `crc32(unhexlify(snapshot_key))` in hex and the commit is `snapshot_key[:40]`. The script then renames paths to `data/<repo>/<scope>/<FileID><ext>`, where scope is derived from path words such as `test`, `src`, `docs`. Finally `obfuscate_creds.py` rewrites **only True values**, character by character. Each char is kept in its class (digit to digit, lower to lower, upper to upper; hex/base32/byte-array/`%xx`/`\xNN`/`\uNNNN` aware), and known vendor prefixes are kept (`ghp_` with a recomputed CRC, `xox?-`, `eyJ` JWT parts re-generated as valid JSON, `AKIA`-like, Google `1//0`). The generator retries until the value contains no `api|key|pass|pwd`, no run of 4 identical chars and no ascending or descending run. Some files (X.509, PEM) are swapped for example files. False and X rows keep their **original** text.
- **Suitability as an outside test set for piifence.** Pro: real context lines and real hard negatives (F/X) from 337 repos, with value-level spans, permissive meta license, and a large txt/md/yml share. Con 1: True values are synthetic random strings, so word-like passwords, passphrases and all-caps or simple passwords are turned into random noise. It will **overstate** recall on our weak categories (passphrases, prose passwords) and cannot test them. Con 2: the context is source code and config, not LLM conversations, with no multi-message or tool-output structure. Con 3: the markup is CredSweeper-centric, so secrets that CredSweeper never proposed are probably under-labelled, and our "true" detections may be scored as FPs. Con 4: getting the data means running git fetches for 337 repos plus their script. The scripts are untrusted, so either run `download_data.py` in a throwaway sandbox or reimplement the ~30 lines of fetch + FileID mapping ourselves (the logic is above). Reimplementing **without** their obfuscation would give us the real leaked values from public repos. That is more realistic, but those values are real secrets, so store them encrypted and never commit them. Suggested use (inference): build a span-level eval. For each meta row, take ±3 lines of context, send it through piifence as a tool_result string, and score masked spans against `[ValueStart, ValueEnd)` T rows; F/X rows give FPs. Report per category and per extension. Stratify by repo if we ever train on it.
- **Extra small test corpus.** `CS/tests/samples/` (250 files, MIT) has hand-written fake cases, especially `doc_various` (109 lines of prose and inline credential shapes like `ID:… PW:…`, `ip (user/pass)`, `login/password-user/pass`, Korean variants), `doc_*_p`/`doc_*_n` (positive and negative pairs), `password_TRUE`/`password_FALSE`, URL, CURL and CMD samples. These are good unit-test seeds for our prose rules. The values are fake.

## 7. Other quick wins

- **Quote awareness as a confidence signal.** CredSweeper skips several filters (camel case, method, array, token-split, allowlist-unquoted) when the value is properly quoted, because quoted literals are more often real secrets. Our key rule already needs quotes. Our model-span guards could also be relaxed for quoted spans that follow a secret-named key.
- **File-type rule for unquoted values.** In code languages that need quotes, an unquoted identifier assigned to `password` is code, so drop it. In `.yaml`, `.env`, `.properties` and `.ini` it is a value. We know the file type for Read tool results (`file_path`) and could apply this rule.
- **`auth_keywords` in the value position.** `(oauth|bot|basic|bearer|apikey|accesskey|ssws|ntlm|token)\s` before the value means `Authorization: Bearer X`, `SSWS X` (Okta) and `Bot X` (Discord) are handled by one template.
- **CLI flags.** `CMD Password` handles `-[A-Za-z_-]*(?i:pass(in|out|word|phrase))` followed by a value, and excludes `file:`, `env:` and `fd:` (openssl). `CURL User Password` handles `curl … -u user:pass`. `SQL Password` handles `CREATE/ALTER USER … IDENTIFIED BY …`, `SET PASSWORD`. All three are useful for Bash tool_use inputs.
- **`IP_ID_PASSWORD_TRIPLE`** handles prose like `<ipv4> user password` with the 3-class value rule. Typical in ops notes pasted into chat.
- **Placeholder/masked detection** via `\*\*\*` (ValueAllowlistCheck) and `<…>` (an ML feature). Also skip our own `$PIIF_SECRET_N` tokens so masking is idempotent (inference, but cheap).
